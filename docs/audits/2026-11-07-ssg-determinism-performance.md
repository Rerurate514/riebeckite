## Scope and Method

### Benchmark

The official `benchmarks/preset-ssg` preset runner was used. It scaffolds real Starter and Showcase sites with `scaffoldRiebeckiteSite` and runs the HonoX/Vite SSG.

- Each sample creates a fresh site and, when required, builds a baseline
- It applies the scenario and runs an incremental build
- It snapshots the incremental `dist`
- It removes `.riebeckite` and `dist`, then runs a clean build
- It snapshots the clean `dist` and compares paths, sizes, and SHA-256
- `--runs 5` repeats each scenario five times and records median, p95, min, max, and stdev
- `--retainOutputs true` keeps the baseline, incremental, and clean output trees

Snapshots sort `readdir` by name and record each file as `{ bytes, sha256 }`. Comparison checks both SHA-256 and size.

### Measurement caveats

- `timingsMs.outputWrite` is an additive sum of concurrent writes, not process wall-clock. It can exceed wall-clock and is not treated as a critical path.
- `spansMs` also accumulates concurrent work. It is used as a stage breakdown, not as a wall-clock total.
- The benchmark `buildOnce` runs only the server build and does not run the `mode: "client"` client build. It therefore contains fewer client assets than a real CLI build.
- During the five-run 100-note batch, the environment restarted and other processes ran (`benchmarks/chaos.mjs --size=1000` and test suites). The later wall-clock and p95 values include contention noise.

## Phase 1: Determinism

### Reproduction

The pre-fix code (equivalent to `e88d403f`) was run for Starter/100. Cold matched, but no-change, body edit, link edit, and publication change differed only in `dist/index.js`.

| Scenario | Incremental | Clean | Difference |
| --- | --- | --- | --- |
| cold | 24,562 ms | 23,956 ms | none |
| no-change | 12,732 ms | 21,823 ms | `index.js` only |
| single-body-edit | 19,537 ms | 25,629 ms | `index.js` only |
| link-edit | 19,983 ms | 24,166 ms | `index.js` only |
| publication-change | 19,771 ms | 22,117 ms | `index.js` only |

The pre-fix `index.js` values were:

- Starter no-change: incremental 860,787 bytes / `54aa6017c36892fc257a44e45d3e5868417f948c548ab9309f099e52b22e62c1`, clean 856,437 bytes / `42035779406ae441eaf905d4a8b7bf0f31ec6660ce25a5cc72ef3ef02f21f32d`
- Showcase publication-change: incremental 867,013 bytes / `ad381a4c923a1744e678a60e3fcd4d24b40d77c00669dbc9651d44fd953624e8`, clean 861,937 bytes / `4482d9466fcab2337692132758fe6c01c2457b86a95e92dd23672d8f3e5d2313`

For Starter no-change, the baseline, incremental, and clean `index.js` files were retained and inspected. Baseline and clean were byte-identical; only the incremental file was 4,350 bytes larger. The first divergence is therefore the incremental Vite server bundle, before output-cache reuse.

### Root cause

`dist/index.js` is the server entry generated by the `@hono/vite-build` Node adapter. Its virtual entry `load()` calls `readdirSync` on `config.publicDir` and `config.build.outDir`, then embeds each top-level entry as `mainApp.use('/<name>', serveStatic(...))` in the server entry.

The riebeckite SSG plugin uses `.riebeckite/build-output` as its staging directory for the server build. Before the fix, `buildStart` copied the previous published `dist` into that staging directory when no client build artifacts existed, then returned. Because `buildStart` runs before the adapter's virtual entry `load()`, previous HTML, `folders/*`, `record-*.html`, and similar files became static paths in the server entry.

That changed Rolldown's module resolution and minified symbol ordering, which changed the size and hash of `index.js`. Minification was not the cause: the mismatch reproduced with `minify: false`, so that experiment was discarded.

### Fix

Only `packages/integrations/honox/src/ssg_plugin.ts` was changed.

1. `configResolved` empties the server staging directory (`.riebeckite/build-output`) before the adapter's `load()` runs.
2. `buildStart` no longer copies the previous `dist` into staging.
3. `generateBundle` restores client artifacts, runs `collectBuildOutputPaths`, and only then copies the previous `dist` into staging. The adapter therefore sees an empty staging directory, while the later SSG output pipeline can still reuse previous outputs.

Moving the copy after `collectBuildOutputPaths` also prevents previous outputs from being classified as client assets in the output plan (`ownerConflictCount` became 0).

An earlier attempt that used `enforce: "pre"` and rewrote `config.build.outDir` to staging in `configResolved` was rejected: it made three Vite server artifacts disappear from `dist` (`missingInDistCount: 3`).

### Bottlenecks

- **Starter/100 no-change**: of the 12.9 s wall median, SSR module load is about 3.3 s; the rest is output-cache validation and reuse. The standalone SSR bundle is rebuilt even when nothing changed.
- **Showcase/100**: wall medians are 41–49 s. SSR module load is about 5–6 s and `toSSG` is about 24–28 s for no-change/full. With 404 planned outputs, route enumeration and HTML generation dominate.
- **cold / full**: `outputDependencyResolution` costs about 6.5 s for Starter and 25 s for Showcase. This is a large fixed cost during full regeneration.
- **Memory**: Starter/100 peaks around 1.0 GB and Showcase/100 around 1.7 GB. Linear extrapolation to 5,000 notes is unsafe, and Showcase is especially memory-constrained.
- **outputWrite**: the reported value can exceed wall-clock (for example 547,736 ms). It is a concurrent sum; it is not yet valid evidence of a wall-clock bottleneck.

### 1,000 and 5,000 notes

The 1,000 and 5,000 note runs did not complete in this session. The five-run 100-note batch alone took about an hour, and the environment restarted during measurement with other processes running. Given Showcase/100 already peaks at about 1.7 GB, a five-run 5,000-note matrix is not realistic on this machine. Missing measurements are not treated as evidence that no problem exists.

## Phase 3: Optimization Evaluation

### Candidate: reuse the standalone SSR bundle

Measurements show `ssrModuleLoad` at about 3.3 s for Starter/100 and 5–6 s for Showcase/100. `ssg/server/standalone.ts` runs a nested Vite build to produce `ssg-server.mjs` and then imports it on every build. If the app's `bundleFingerprint` has not changed, the bundle could be reused.

The expected gain is roughly 10–25% of no-change wall-clock. It was not implemented because:

- `bundleFingerprint` covers the app, config files, local workspace packages, and `NODE_ENV` / `VITE_*`, but not every programmatic Vite `define`, `oxc`, or plugin option.
- A new derived cache would need additional validation for `RIEBECKITE_SSG_FULL_REGENERATION`, the client manifest, publication boundaries, and failure recovery.
- Importing a stale bundle after a failed build could publish incorrect HTML. A safe design needs an atomic marker and rebuild-on-corruption behavior, which could not be validated sufficiently in the remaining time.

### Rejected approaches

- **Disabling minification**: `minify: false` still produced a mismatch. It is not the cause.
- **Rewriting `build.outDir` to staging in `configResolved`**: three server artifacts disappeared from `dist`.
- **Limiting output-write concurrency**: `outputWriteTimeMs` is an additive concurrent sum and exceeds wall-clock, so there is no wall-clock evidence for a gain.

## Risks

- The fix depends on `@hono/vite-build` scanning `config.build.outDir` in its virtual entry. A change in that dependency could reintroduce the bug.
- The copy in `generateBundle` must stay after client artifact restoration and `collectBuildOutputPaths`. Reordering it reintroduces output-plan contamination.
- The benchmark omits the client build, so real-site wall-clock may be higher than reported.
- The 100-note measurements were affected by concurrent processes. Use them for relative comparison in this environment, not as universal absolute values.
- Showcase memory usage makes a five-run 5,000-note measurement impractical.

## Next Steps

1. Measure 1,000 notes at least once and compare scaling with 100 notes.
2. Evaluate 5,000-note memory limits first; design streaming or partitioned generation if needed.
3. Implement standalone SSR bundle reuse with a marker, rebuild-on-corruption, and full-regeneration semantics, then verify wall-clock with A/B runs.
4. Add a benchmark that includes the client build to match real CLI behavior.
5. Split `outputWrite` into concurrency and critical-path measurements.
