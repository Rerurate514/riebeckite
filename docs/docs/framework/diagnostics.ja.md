# 診断

診断は、Riebeckite の設定やコンテンツ、[[glossary/plugin|プラグイン]]、実行環境に問題がないかを検査し、開発者に報告するための仕組みです。

単にエラーメッセージを `console.log` へ出すのではなく、

- 何が問題なのか
- どこで問題が起きているのか
- どの程度重要なのか
- どう直せばよいのか

といった情報を、Riebeckite が扱える共通形式の診断情報（diagnostic）として表現します。

これにより、Core や各プラグインが見つけた問題を扱えます。開発用の診断パッケージはその結果をシリアライズ可能なレポートに変換し、`doctor` と開発用インスペクターで共有します。

## 診断の流れ

プラグインは `addDiagnostics` を使って独自の診断を追加できます。

追加された診断は Core やインテグレーションによって集約され、主に `check` や `doctor` から利用されます。

診断を追加するときは、可能な限り次の情報を明確にしてください。

- 問題が発生する条件
- 問題のあるコンテンツや設定
- 問題の重要度（severity）
- 修正方法（remediation）

たとえば「設定が不正です」とだけ報告するのではなく、「どの設定が不正で、どのように変更すればよいか」まで分かる診断を推奨します。

## `check` と `doctor`

`check` と `doctor` は役割が少し異なります。

`check` は主に設定やプラグインの構成が正しいかを検査します。

`doctor` はそれに加えて、Riebeckite が正常に動作できる状態かをより広く検査します。

`doctor` では、1つの検査に失敗しても、可能な限り他の独立した検査を続行します。そのため、複数の問題がある場合でも一度の実行でまとめて確認できます。

問題が見つかった場合、コマンドは非ゼロの終了コードで終了します。

観測できない項目は推測せず、利用できないことを明示します。診断のためだけに[[glossary/full-build|フルビルド]]は実行しません。新しく収集する診断には安定した fingerprint が付き、JSON の summary には既存の severity 件数を維持したまま unavailable ・ skipped ・ category ・ code ごとの件数が追加されます。

開発用インスペクターは Vite の開発サーバーからだけ利用でき、同じレポートを Shadow DOM のパネルに表示します。本番のクライアントモジュールやエンドポイントには含まれません。パネルはまず診断を表示し、「依存関係」と「出力」のタブは別のエンドポイントから読み込みます。そのため、大きな出力計画が他のタブの表示を遅らせません。診断はテキスト、severity、category、code で絞り込めます。現在ページによる絞り込みには、完了済みビルドスナップショットに含まれる source-to-page mapping を使います。推測のために Markdown を再解析したり、別のビルドを実行したりはしません。

出力エンドポイントはサーバー側で絞り込みとページングを行うため、ブラウザーがすべての出力行を受け取ることはありません。affected / unchanged / removed の出力をページ送りし、kind、status、テキストで絞り込めます。出力パスから依存関係を逆引きでき、コンテンツ変更の影響を直接受ける出力も一覧できます。完全再生成の理由は、[[glossary/build-state|ビルド状態]]、キャッシュ契約、[[glossary/pipeline|パイプライン]]の[[glossary/fingerprint|フィンガープリント]]、出力変更セットに根拠がある場合だけ表示し、それ以外は unknown として報告します。

## コンテンツ ID の検査

Riebeckite では、コンテンツを継続的に識別するための「安定コンテンツ ID」を設定できます。

通常は[[glossary/frontmatter|フロントマター]]の `id` を使用します。

```yaml
---
id: my-article
---
```

この ID は、たとえば analytics プラグインがページごとの閲覧数を記録するときなど、URL とは別にコンテンツそのものを識別したい場合に利用されます。

診断プラグインは、コンテンツ ID について次の問題を検査します。

| コード | 既定の重要度 | 条件 |
| --- | --- | --- |
| `duplicate-content-id` | error | 複数の公開コンテンツが同じ ID を使用している |
| `invalid-content-id` | error | `id` がコンテンツ ID のルールを満たしていない |

たとえば、2つの記事が同じ ID を持っていると、analytics などで別の記事のデータが同じコンテンツとして扱われる可能性があります。

これらは analytics 専用の検査ではありません。コンテンツ ID を利用するすべての機能に共通する整合性チェックとして、診断が担当します。

## サイト全体のコンテンツ整合性

診断プラグインは、公開サイト内のリンクや参照が正しく解決できるかも検査します。

たとえば、次のような問題を検出します。

- 存在しないページへのリンク
- 解決できない Wiki リンク
- 存在しない画像や添付ファイルへの参照
- 複数のコンテンツによる[[glossary/public-path|公開パス]]の重複
- 存在しない転送先への[[glossary/redirect|リダイレクト]]
- 循環しているリダイレクト

これらは `content-integrity:*` の診断として報告されます。

### どの情報を使って検査するのか

整合性検査では、Riebeckite がすでに解決した公開コンテンツや公開パスの情報を使用します。

そのため、診断のためだけに Markdown をもう一度解析したり、コンテンツを最初から読み直したりすることはありません。

また、パーマリンク、[[glossary/alias|エイリアス]]、名前変更、[[glossary/localization|多言語化]]、公開・除外設定などによって最終的な[[glossary/public-location|公開先]]が変わっている場合も、Riebeckite が解決した結果を基準に検査します。

### HTML の品質検査との違い

診断が担当するのは、主にサイト全体の参照や構成の整合性です。

一方で、

- 画像に適切な `alt` があるか
- 見出し構造が適切か
- 生成された HTML に問題がないか

といった個々のページの HTML 品質は `@riebeckite/plugin-quality` が担当します。

## 非推奨 API

API ライフサイクルのメタデータは、非推奨の公開 API を宣言します。診断はメタデータ自体を検査し、メタデータが設定パスやプラグインオプションを指定している場合は、現在の設定でそれが使われているかも報告します。

| コード | 既定の重要度 | 条件 |
| --- | --- | --- |
| `RB-API-001` | warning | 非推奨 API が設定で使われている |
| `RB-API-002` | error | API ライフサイクルのメタデータが不正 |

`RB-API-001` には API の ID、パッケージ、非推奨になったバージョン、代替 API、削除バージョン（未確定の場合は `not confirmed`）、移行ガイド、理由、検出した箇所が含まれます。`RB-API-002` は不正なフィールドと、検証に失敗した理由を報告します。

非推奨の警告は既定では `check` や `doctor` を失敗させません。CI で失敗として扱いたい場合は `doctor --fail-on warning` を使います。メタデータが不正な場合は、レジストリが API を正確に説明できないためエラーになります。メタデータのフィールドと削除の方針については [API ライフサイクル](../reference/api-lifecycle.ja.md) を参照してください。

## プラグインからページやアセットを公開する場合

プラグインが独自のページ、生成ファイル、アセットなどを公開する場合は、Riebeckite が提供する対応する仕組みを使って登録してください。

正しく登録された公開先は診断からも認識されます。

そのため、たとえばプラグインが `/explore` というページを正式に公開していれば、

```text
/explore
```

へのリンクが「存在しないページ」として誤って報告されることはありません。

## アセットの状態

`doctor` はコンテンツルートのアセットも読み取り専用で検査します。Markdown 以外のファイルを SHA-256 でハッシュ化し、解決済みコンテンツからの参照を数え、未使用または未使用の可能性があるアセット、重複グループ、大きなファイル、旧形式の画像を報告します。これらの検出は `ASSET_*` コードと `content` カテゴリを使います。アセット診断がファイルを削除することはありません。修正するかどうかは、参照パスを確認したうえで人が判断します。

同じ検査は `riebeckite inspect assets` と Inspector の Assets タブからも実行できます。ノートから参照される画像については既存の画像専用 `unused-asset` 検査が引き続き基準となるため、`ASSET_UNUSED` はその検査が報告済みのパスを除外します。

## 診断を実装するときのルール

診断を追加するときは、次の原則に従ってください。

- オプション検証ではファイルの読み込みや状態変更を行わない
- 安全な結果を判断できない場合は、推測して処理を続けず診断として報告する
- スタックトレース、トークン、不要な絶対パスをユーザー向けメッセージへ含めない
- メッセージ文字列ではなく、安定した診断識別子を使って問題を識別する
- 可能な限り具体的な修正方法を示す
- 診断の生成中に自動修正、ビルド、キャッシュ更新、状態更新を行わない

診断は問題を**発見して説明する仕組み**です。問題を自動的に修正したり、ビルド状態を変更したりする仕組みではありません。

現在の状態そのものを確認したい場合は[インスペクター](./inspector.ja.md)、ログやトレースを確認したい場合は[可観測性](./observability.ja.md)を参照してください。
