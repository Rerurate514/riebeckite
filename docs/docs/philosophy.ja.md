# 設計思想

Riebeckite は Markdown と Obsidian のノートから Web サイトを構築する静的サイトフレームワークです。

ノートとサイトは、フレームワークより長く残ります。テーマ変更やツール移行で記事が壊れないよう、Riebeckite は**利用者が自分のコンテンツとサイトを所有し、必要な自由度を保ちながら、余計な複雑さを意識せずに使えること**を設計の軸に置いています。ここに書くのは機能一覧ではなく判断の基準です。実装が届いていない箇所は、原則を変える理由ではなく、修正すべき不具合か検討すべき論点です。

## 設計原則

### 1. コンテンツとサイトの所有権は利用者に残す

ファイルは常に手元の Markdown と Obsidian Vault にあります。基本的には、独自記法への書き換えが不要なので、別のツールへ移ってもそのまま残ります。設定、生成コード（`app/`）、ビルド出力、デプロイ先も利用者が管理でき、特定のホスティング先に縛られません。ただし、このフレームワークではCloudflare Workerを推奨しています。

### 2. 基本は簡単に、複雑さは必要なときだけ

高度な自由度は基本的な利用を複雑にする理由にはなりません。ノートを書いて公開するだけならプリセットと最小限の設定で完結し、内部構造を意識せずに使える設計を目指します。レイアウト変更や HonoX アプリとしての拡張、プラグイン開発は、必要になった段階で触れれば十分です。自動化で手間を減らす際も、設定や出力の根拠を追跡できる明示性を保ちます。

### 3. Web 標準と既存エコシステムを尊重する

Markdown 変換の unified、描画とルーティングの HonoX、バンドルの Vite、UI の TypeScript・JSX・CSS、配布の npm をそのまま使い、既存技術で解決できることに独自仕様は作りません。固有の API はリンク解決や公開境界、プラグイン連携など、汎用ツールだけでは安全に扱えない部分に限定します。

### 4. 静的生成を基本とし、安全性をビルド時に担保する

ビルド時に解決できる処理はビルド時に済ませ、JavaScript なしでも読める静的 HTML を基本とします。検索やグラフなどの対話性は必要なページにだけ追加し、公開サイトの実行環境はビルド用のキャッシュやローカルファイルを参照しません。生 HTML のサニタイズと、非公開ノートを検索や RSS など派生出力から除外する公開境界も、ビルド時に確定させます。

### 5. 責務の境界を明確にし、長期的な保守性を保つ

Core、Plugin、Theme、Integration、Application の役割を分け、依存の向きを Core 側へ揃えています。Theme は CSS と視覚トークンだけを担うため、見た目を切り替えても記事や URL は壊れません。抽象化自体を目的にせず、Core の肥大化を防ぎ、長期的に理解・変更・移行しやすい設計を保ちます。

## トレードオフ

価値がぶつかる場合は、次の優先順位で判断します。既定を覆すには、測定やテスト、移行手順などの根拠が必要です。

- Obsidian 互換性を独自拡張より優先します。拡張記法は、既存のノートがそのまま読めるよう、標準の Markdown を壊さない範囲でプラグインとして提供します。
- 正確性と再現性をビルド速度より優先します。増分ビルドに曖昧さがあればフルビルドへ戻します。セキュリティと公開境界は常に守る制約です。
- 長期的な保守性を 1.0 前の API 固定より優先します。`0.x` の間は設計の修正を先に行い、破壊的変更には移行手順を記録します（1.0 以降は SemVer）。

## 非目標

- Obsidian や Web 標準の置き換えは目指しません。エディタの再実装や、HonoX・Vite・CSS を隠す独自テンプレート言語は作りません。
- ホスト型 CMS は運営しません。記事をブラウザの管理画面とデータベースに囲い込まず、ファイルベースのノートを公開するフレームワークに徹します。
- すべての機能を Core に置くことはしません。検索・グラフ・OG 画像などはプラグインへ分離します。
