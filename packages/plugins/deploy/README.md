# @riebeckite/plugin-deploy

<!-- Generated from docs/docs/plugins/deploy.md. Edit the canonical documentation in docs/docs/plugins and run `pnpm docs:sync`. -->

Static hosting output helpers for Riebeckite. The plugin prepares the files a
deploy target needs and emits them through the build's generated-output sink.
It does not upload anything and never writes to the filesystem.

[日本語](./README_ja.md)

## What it does

- Generates provider-specific redirect and header files during `riebeckite build`.
- Reads redirects only from `manifest.publicRedirects`.
- Supports Cloudflare Pages, Cloudflare Workers, Netlify, Vercel, and GitHub
  Pages.

## What it does not do

- It does not upload files, authenticate with a provider, or invalidate caches.
- It does not deploy the site. Upload the build output with your provider's
  normal deploy step, or use the publication workflow's `publish run --execute`
  when your site is configured for it.
- `riebeckite deploy setup` is a separate CLI helper that prepares Cloudflare
  configuration. It also does not upload anything.

## Overview

`deploy()` reads public redirects from the content manifest and plans the
provider-specific files for Cloudflare Pages, Cloudflare Workers, Netlify,
Vercel, or GitHub Pages. All planning is pure and deterministic: no timestamps,
no randomness, and a stable path order.

## Usage

```ts
import { defineConfig } from "@riebeckite/core";
import { deploy } from "@riebeckite/plugin-deploy";

export default defineConfig({
  plugins: [
    deploy({
      provider: ["cloudflare-workers", "github-pages"],
      cname: "example.com",
      headers: { "X-Frame-Options": "DENY" },
    }),
  ],
});
```

Redirects come only from `manifest.publicRedirects`, so unpublished notes never
leak their old paths into deploy files. A redirect whose target slug is missing
is skipped and reported with a `deploy-unresolved-redirect` diagnostic.

## Per-provider output

| Provider | Files |
| --- | --- |
| `cloudflare-pages`, `cloudflare-workers`, `netlify` | `_redirects` (when redirects exist), `_headers` (when headers are configured) |
| `vercel` | `vercel.json` |
| `github-pages` | `.nojekyll`, `404.html`, `CNAME` (when configured), one `<from>/index.html` meta-refresh stub per redirect |

`cloudflare-workers` produces the same files as `cloudflare-pages`, because
Workers Static Assets reads both `_redirects` and `_headers`. Cloudflare applies
`_redirects` only to static asset responses, not to responses generated by
Worker code.

GitHub Pages has no `_redirects` syntax, so every redirect becomes an HTML stub
with a meta refresh and a `<link rel="canonical">`. A redirect from `/` is
skipped because the root cannot be stubbed.

## Deploying the generated files

Run the normal build:

```sh
npm exec riebeckite build
```

The files are written into the build output (for example `dist/_redirects`).
Upload that directory with your provider's deploy step. This plugin stops at
file generation; it has no credentials and performs no upload.

If your site uses the publication workflow, `publish run --execute` performs
the configured publication step. `deploy setup` only prepares Cloudflare
configuration.

## Public API

- `deploy(options: DeployOptions): RiebeckitePlugin`
- `planDeployOutputs({ provider, redirects, options }): DeployOutput[]`
- `renderRedirectLines(redirects): string`
- `renderVercelConfig({ redirects, options }): string`
- `renderRedirectStub(redirect): string`

## Notes

- Multiple providers are unioned. Identical files collapse into one; the same
  path with different content throws.
- Redirect `from` values are resolved (`.` and `..` segments) before they become
  output paths, and every planned path passes `normalizeGeneratedOutputPath`.
- Uploading, cache invalidation, and provider authentication are out of scope.
