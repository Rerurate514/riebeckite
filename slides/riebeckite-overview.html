Background

出発点は、
Quartz 4への不満だった

Markdownを書けばサイトになる。その基本はよくできていた。問題は、その先にあった。

クライアントUI
HooksとDOM操作。普段使っているコンポーネントの書き方ではなかった。
構成の分離
Vaultとサイトのコードを分けて管理するのが難しい。
アップグレード
v4からv5へ移るとき、サイトのセットアップをやり直すことになった。
Markdownは入力であって、アーキテクチャの中心ではありません。
README_ja — Riebeckiteを選ぶ理由
だから、生成物の前提を変えた。 設定済みの製品ではなく、普通のHonoXアプリケーションを出力する。
What it is

Markdownを、自分のコードで組むサイトへ

Riebeckiteは、ObsidianノートやMarkdownを静的サイトとして公開するためのフレームワークです。生成されるのは、@riebeckite/* を依存に持つ普通のHonoXアプリケーションです。

STACK

いつもの道具

TypeScript、JSX、HonoX、npm。独自のテンプレート言語を覚える必要はない。

CONTENT

コンテンツは手元に

フォルダでも、既存のVaultでも、別リポジトリでも。content.directoryで指定する。

ECOSYSTEM

npmで拡張する

PluginもThemeも普通のnpmパッケージ。公式に72のPluginと6のThemeがある。

Ownership サイトはフレームワークの付属物ではない。更新は依存パッケージの更新で済み、自分のタイミングでバージョンを上げられる。
Principles

四つの設計原則

フレームワークの形を決めているのは、機能の数ではなく境界の引き方です。

01

内側は外側を知らない

CoreはHonoX、Vite、Cloudflare、特定のPluginを知らない。

02

Markdownは入力

ページ、URL、リンク、アセットはビルド時に解決する。Markdownはアーキテクチャの中心ではない。

03

静的を基準にする

JavaScriptがなくても本文が読める。動きは必要な場所だけに足す。

04

permalinkが正

ファイルパスからURLを再計算しない。解決済みのpermalinkだけを公開URLとして使う。

迷ったら、その機能を成立させるために必要な、最も内側のpackageに置く。

Content system

コンテンツが、公開URLになるまで

ContentSourceが「どこから読むか」、ContentManagerが「どう扱うか」を担当する。

ContentSource scan · read · hash

ファイル、Vault、別リポジトリ。保存場所を抽象化する。

どこから読むか
→
ContentManager location · parse · hooks

公開URLを解決し、Pluginを通してコンテンツを処理する。

どう扱うか
→
Manifest / Graph pages · links · assets

サイト全体の事実をひとつのmanifestにまとめる。

何が公開されるか
→
HonoX build routes · islands

静的HTMLと、必要なブラウザコードを出力する。

どう届けるか
ファイルパス content/posts/hello.md
→
論理パス posts/hello
→
公開URL /blog/hello/ source of truth

ファイルパスからURLを推測しない。Pluginやconfigが解決したpermalinkだけを使う。

Plugin API

Pluginは、ひとつの関数から

definePlugin()に、必要な拡張ポイントだけを渡す。サイト内のファイルでも、npmパッケージでも同じ仕組み。

extensions/local-plugin.tsTypeScript
import { definePlugin } from "@riebeckite/core";

export function localPlugin() {
  return definePlugin({
    name: "local",
    assets: [
      {
        pluginName: "local",
        kind: "style",
        moduleSpecifier: "/extensions/plugin.css",
      },
    ],
  });
}

表示

nameだけでもPluginになる。必要になった拡張ポイントを、ひとつずつ足していく。

配布しないなら、extensions/local-plugin.ts に置くだけでよい。packageにするのは、他のサイトでも使うときだけ。

Build

ビルドは、変更だけをやり直す

前回の結果を使い、変更された部分だけを処理する。stateが使えなければ、最初からやり直せばいい。

  1. 01
    設定とPluginを読む

    configを解決し、依存関係を検証する。

  2. 02
    コンテンツを読み、変換する

    Plugin hooksを通してMarkdownを処理する。

  3. 03
    公開URL・リンク・アセットを確定する

    サイト全体のmanifestとcontent graphを作る。

  4. 04
    HonoXでbuildする

    静的HTMLと、必要なislandsを生成する。

Incremental build

.riebeckite/build/content-state.json
  • 変更されたコンテンツだけを再利用する
  • 安全に再利用できるか判断できなければfull build
  • buildが失敗したら、前回の成功状態を保持する
  • --full で最初から処理する

Build-time と Runtime

Build-time

CLI · Doctor · Inspector · cache · profile

Runtime

生成済みアプリと安定したcontent dataだけ。Workersはstateを読まない。

高速化のためのstateがなくても、同じサイトを正しく生成できる。これを前提にしている。

SPA navigation

SPAは、静的な土台を壊さない

サーバー描画を基準に、ブラウザ側だけを強化する。置き換えるのはページのルートで、HTML文書全体ではない。

riebeckite.dev/docs
Header / global UIstays
main#main-content replaced
Footerstays
  1. 01
    クリックを横取りし、次のHTMLを取得する

    通常のリンク遷移を、fetchに置き換える。

  2. 02
    ページスコープをunmountし、headを更新する

    後始末をしてから、メタデータを差し替える。

  3. 03
    mainを置き換え、islandsをhydrateする

    シェルは残したまま、ページのルートだけを更新する。

  4. 04
    履歴、スクロール、フォーカスを更新する

    最後にページスコープをmountし、navigationイベントを発火する。

spa: { prefetch: "hover", viewTransitions: true } で、先読みと画面遷移を有効にできる。

Workflow

作る、確かめる、届ける

雛形の生成からデプロイまで、CLIで完結する。

terminalquick start
# 雛形を生成
$ npx create-riebeckite

# 依存を入れて、開発サーバーを起動
$ cd my-site
$ npm install
$ npm exec riebeckite dev

# 静的サイトを dist/ へ
$ npm exec riebeckite build
dev開発サーバーを起動する
check設定とPluginを検証する
doctor環境、content、output、Themeを診断する（--fix）
inspectconfig、plugins、content、graph、buildの解決結果を見る
build静的サイトを生成する（--fullで全処理）
deployCloudflare Workersへ公開する

プリセットは starter / showcase / minimal / empty。--list-presets で一覧できる。

Fit

向いている人、向かない人

Riebeckiteが向くのは、サイトを自分のプロダクトとして持ちたい人。

向いている

  • ObsidianやMarkdownで書いている
  • サイトのUIも自分で作りたい
  • TypeScript / JSX / HonoXを普段使っている
  • コンテンツをサイトの外に置きたい

向かない

  • コードを書かずにサイトを完成させたい
  • 既製テーマを選ぶだけで十分
  • Markdownの表示だけを最速で公開したい

表示だけなら、ホスティング型のサービスで足りる。サイトの構造まで自分で決めたいなら、ここから始める。
